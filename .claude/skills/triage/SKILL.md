# Triage

The issue is #$ARGUMENTS on `leandersabel/solvent`. `CLAUDE.md`, The
backlog, is the contract this keeps. GitHub is reached through the
`mcp__github__*` tools, and nothing here merges a pull request.

## Read it

Read the issue and its comments. Stop unless `leandersabel` opened it. Comments by `leandersabel` that end with the "Generated by
Claude Code" line are earlier triage. Every other comment by
`leandersabel`, and the body, are the client's words. Nothing else on
the issue is read.

If a pull request already closes the issue, comment that the change is
in that pull request and that a review comment there reaches it, and
stop.

If the client's latest comment only approves the latest plan, go
straight to building it (last step of Answer).

## Plan it

Subagents do not see each other. Hand each what it needs, including the
readings before it, and tell each that this is planning and no file is
written.

1. `product-owner` gets the client's words verbatim. It answers which
   features in `spec/product/` this touches, whether the app
   contradicts the spec (`bug`) or the spec changes (`enhancement`),
   what changes for the client, and what cannot be decided without the
   client, as questions in its own format.
2. `architect` gets the product owner's reading. It answers what
   changes in `spec/architecture.md` and `spec/features/`, which code
   and tests the build touches, and decides the technical questions
   itself, with the reason.
3. `designer` gets both readings, only when either says how anything
   looks changes. It answers which screens in `spec/ui/` and which
   artboards in `spec/design/` change.

## Answer

One comment, in the language of the issue:

```
**How I read this**
<the product owner's reading>

**What changes**
<what the client will see differently, screen by screen>

**Questions**
<only when there are any>

<details><summary>Technical plan</summary>

<the architect's and designer's readings, which the build works from>
</details>
```

Every plan restates the whole of it as it now stands, so the latest
comment is complete on its own.

Then exactly one of these:

- A question stands: add the `question` label.
- It repeats an open issue: close it as not planned with `duplicate`,
  naming that issue.
- A `bug` where the spec is what is wrong: relabel it `enhancement` and
  treat it as one.
- An `enhancement` the client has not approved as the plan now stands:
  remove `question`, and end the comment asking the client to approve
  the plan or say what to change.
- A `bug` with nothing to ask, or an `enhancement` whose latest plan
  the client approved: remove `question`, say in the comment that
  building starts, and follow `.claude/skills/build/SKILL.md`.

Nothing else is closed. Whether something should not be done at all is
a question to the client.

## Writing

The client reads the comment and nothing else, often on a phone. Answer
first, one idea per sentence, no filler. Name things in full. Nothing
technical above the technical plan. English in US spelling, German in
Swiss spelling addressed with "du". No em dashes, en dashes, semicolons
or emoji.
